# Rust 最佳实践规范

## 1. 范围与基线

本文约定 Rust 业务代码、库代码和底层实现代码的设计、实现、测试、审查与文档。语言基线采用 Rust 2024 Edition；项目的最低支持 Rust 版本由各自 `rust-version` 明确固定，不默认假设所有项目使用同一稳定版本。

主要参考：

- The Rust Programming Language
- Rust Edition Guide
- Rust Reference
- Rust API Guidelines
- Cargo Book
- rustdoc、rustfmt、Clippy 官方文档
- The Rustonomicon
- Asynchronous Programming in Rust

核心立场：优先 safe Rust、清晰契约、可测试设计和可维护抽象；性能优化必须先测量，再修改。

---

## 2. 设计原则

1. 安全优先：默认使用 safe Rust；`unsafe` 只用于无法用安全抽象合理表达的底层边界。
2. 类型优先：用类型表达领域含义，减少裸布尔值、裸字符串和无约束整数扩散。
3. 所有权清晰：函数输入、输出、可变性和副作用应能从签名与文档中理解。
4. 错误是值：可恢复失败使用 `Result`；可选状态优先考虑 `Option`；不变量破坏才考虑 panic。
5. 边界明确：模块、crate、线程、异步任务和 FFI 边界都应有明确契约。
6. 抽象不过早：先保证清晰和正确，再根据测试、profile 和基准数据优化。
7. 工具只是保障：rustfmt、Clippy、rustdoc、Cargo 和测试补充人工判断，不能替代架构审查。

## 3. 命名与 API 设计

### 3.1 命名

命名遵循 RFC 430 与 Rust API Guidelines：

- 类型、trait、枚举和枚举变体使用 `UpperCamelCase`。
- 函数、方法、变量、参数、模块和 crate 使用 `snake_case`。
- 常量和静态项使用 `SCREAMING_SNAKE_CASE`。
- 生命周期使用短小、语义清晰的名称；通用场景可使用传统短名。
- 缩写在 `UpperCamelCase` 中按一个词处理，例如优先使用 `Uuid` 而不是 `UUID`。
- 缩写在 `snake_case` 中保持小写。
- 集合产生迭代器的方法优先使用 `iter`、`iter_mut`、`into_iter`；对应迭代器类型名应与产生它的方法一致。
- feature 名称应描述能力，不应使用占位词或模糊词。

### 3.2 转换方法

转换方法遵循 Rust API Guidelines 的成本语义：

- `as_` 表示低成本借用视图，通常从借用返回借用。
- `to_` 表示可能复制、分配或产生新的 owned 值。
- `into_` 表示消耗所有权，通常返回另一种 owned 表示。
- 标准转换能力优先实现或使用 `From`、`Into`、`AsRef`、`AsMut`。
- 转换方法应定义在参与转换的更具体类型上。
- getter 不加 `get_` 前缀；可变访问可使用 `_mut` 后缀。

### 3.3 API 形态

- 公共类型的字段默认私有，通过方法暴露受控访问。
- 构造函数应尽量保证对象创建后处于有效状态。
- 避免出参风格；优先通过返回值表达结果。
- 参数语义不适合用裸 `bool` 或裸 `Option` 表达时，使用枚举、newtype 或专门类型。
- 泛型约束只声明实际需要的能力，不要为未来需求提前扩大约束。
- 函数应避免对调用者做不必要假设；调用者应尽量决定复制、放置和持有数据的时机。
- trait 若可能作为 trait object 使用，应保持 object-safe。
- 不希望下游实现的 trait 应明确密封。
- 运算符重载必须保持直觉一致，不隐藏昂贵或 surprising 的行为。
- 公共类型应优先实现 `Debug`；并根据语义考虑 `Clone`、`PartialEq`、`Eq`、`Hash`、`Default`、`Display`、`Send`、`Sync`。
- 集合类数据结构在合理时实现 `FromIterator` 和 `Extend`。
- 错误类型应有意义、可诊断、可下游判断，并遵循 Rust 对 `Error` 类型的惯用行为。

## 4. 所有权、借用与资源

- 函数参数选择最宽泛且语义正确的形式；文本只读通常使用字符串借用，集合只读通常使用切片。
- 只有函数确实需要拥有数据时才接收 owned 类型。
- 克隆必须表达语义上的独立副本，或经过测量确认必要；不要机械地“永不克隆”。
- 可变性范围尽量收窄；能使用不可变借用时不要使用可变借用。
- 生命周期从真实数据流推导，不为了绕过借用检查而随意复制或延长生命周期。
- `Cow` 适合“多数情况借用、少数情况需要 owned”的场景，但不应作为默认参数类型。
- 自定义类型不应随意实现 `Deref` 或 `DerefMut`；它们主要用于智能指针语义。
- 文件、锁、网络连接、进程句柄、临时目录等资源依赖 RAII 自动释放。
- 析构函数不应失败；可能阻塞的析构路径应提供显式关闭或清理的替代方案。
- 共享所有权只在确实需要多所有者或跨边界延长生命周期时使用。
- 公共 API 不应让调用者推测隐藏的资源生命周期、锁范围或后台任务归属。

## 5. 类型建模

- 领域含义不同的值使用不同类型区分，避免裸字符串和裸整数扩散。
- Newtype 适合包裹 ID、数量、单位、外部系统标识、校验值等易混淆概念。
- 枚举适合表达有限状态和互斥模式，并让编译器强制穷举。
- 标志集合适合专门的位标志抽象，而不是把普通枚举当位集合滥用。
- 复杂对象的构造可使用 builder，但要避免为了小对象引入过重流程。
- 避免用大量可选字段拼装“半有效对象”。
- 状态机应让非法状态难以表示，而不是在多个函数中重复校验。
- 类型不应重复暴露派生 trait 的完整泛型约束；实现细节尽量封装。
- Newtype 应封装内部表示，避免泄漏无意义的内部结构。

## 6. 控制流与表达式

- 常见失败、非法输入、未初始化依赖应提前返回，减少嵌套。
- `match` 用于需要穷举所有分支的枚举逻辑。
- `if let` 适合只关心一种模式的场景。
- `let else` 适合作为卫语句提取有效值。
- Rust 是表达式语言，应利用表达式减少临时变量和重复赋值。
- 循环与迭代器按可读性和状态复杂度选择：迭代器适合表达转换流水线，普通循环适合复杂状态推进、提前终止或跨迭代共享状态。
- 避免隐藏副作用的复杂链式调用。
- 避免在长表达式中混合多层匹配、错误转换、索引和副作用。
- 中间命名值用于降低认知负担时是合理的，不应为了追求“短”牺牲可读性。

## 7. 错误处理

- 可恢复错误返回 `Result`，不要用日志、全局状态或 panic 表达业务失败。
- panic 表示程序员错误、不变量破坏或程序无法继续的安全状态。
- 公共库 API 应返回有意义的错误类型，而不是把 panic 作为普通失败路径。
- 应用层可以合并统一错误类型，但应保留足够上下文用于诊断。
- 禁止静默吞掉错误；降级路径必须记录原因、影响和最终结果。
- `unwrap` 和 `expect` 只允许用于测试、原型或已有证明的不变量；生产代码中使用时应说明为什么不会失败。
- 错误信息应说明失败动作、失败对象、关键输入、边界值和可能的后续处理。
- 第三方错误辅助库不是 Rust 语言规范的一部分；是否使用属于项目选型。
- 错误类型应避免让下游依赖字符串匹配来分支处理。
- 对外错误应区分：调用方可以修复、调用方应重试、系统状态不可恢复、程序存在 bug。

## 8. 并发与异步

- 先区分并行和并发，再选择线程、异步、消息流水线、任务池或事件驱动模型。
- CPU 密集工作通常更适合线程或专用并行机制；高数量 I/O 等待更适合异步模型。
- Rust 的异步语义需要运行时支持；runtime 是项目级依赖决策。
- 线程间共享状态必须有明确同步策略；消息传递适合所有权转移和任务解耦。
- 锁的保护范围应尽量小，避免在锁内执行长耗时操作、外部调用或可能回调回自身的逻辑。
- 死锁审查应覆盖锁顺序、回调、取消、超时和资源释放路径。
- `Send` 和 `Sync` 是编译期约束；公共 API 应显式表达线程安全假设。
- 异步代码不应执行阻塞 I/O、长 CPU 循环或同步等待；这类工作应移交独立线程或专用池。
- 异步取消是正常路径，不是异常路径；跨 await 点的状态必须保持一致。
- 不要假设 future 一定会运行完成；取消、超时、关闭和资源恢复路径必须设计。
- 同步互斥量和异步任务的使用场景需要谨慎区分，避免跨 await 持有不兼容的锁。
- 原子操作和无锁结构只有在测量证明锁成本显著时才考虑，并必须重点审查内存顺序和可伸缩性。

---

## 9. 性能

- 性能规则以测量为准，不凭直觉优化。
- 先选择合适的算法和数据结构，再做局部微优化。
- release 构建才代表发布性能；debug 数据不能直接用于判断优化效果。
- 基准应覆盖真实数据形状、并发压力、冷热路径、缓存行为和边界条件。
- 迭代器和泛型通常可被良好优化，但零开销不是保证；应结合 profile、构建产物和基准验证。
- 静态分发可减少运行时间接调用，但可能增加编译时间和代码体积。
- 动态分发适合运行时多态、类型擦除和异构集合，不应仅为了“看起来简单”而默认使用。
- 避免不必要的堆分配、深层克隆和重复格式转换。
- 预分配容量只在已知规模或已测量分配成本时作为优化手段。
- `#[inline]` 不是自动加速开关；应基于跨 crate 热点、profile 或基准结果使用。
- `opt-level`、LTO、codegen units、panic strategy、debuginfo、strip 等构建配置都存在运行性能、体积、编译时间、可调试性和异常处理之间的权衡，必须作为项目级决策验证后启用。
- panic 策略影响互操作和异常恢复；不能把 `abort` 当成无成本优化。
- 第三方零拷贝缓冲区、小集合优化、对象池或 arena 只在热点路径有测量收益时引入。

## 10. Unsafe Rust

- `unsafe` 是最后手段，不是性能默认方案。
- 所有 `unsafe` 代码都在维护 safe Rust 的不变量；safe 接口必须保证任意安全调用都不会触发未定义行为。
- 每个包含 `unsafe` 的函数、类型或模块都应说明安全契约：别名、生命周期、对齐、初始化状态、线程约束、平台假设和外部系统要求。
- `unsafe` 应封装在尽可能小的安全接口内部，调用方不应承担不必要的底层契约。
- 不要通过拆小 `unsafe` block 制造安全错觉；关键是证明整段操作满足所有不变量。
- 优先寻找标准库、官方生态或成熟安全抽象替代方案。
- `unsafe` 代码必须有针对性测试，并尽量使用 Miri、fuzzing、sanitizers、目标平台测试或形式化检查验证。
- 修改 unsafe 附近代码时必须重新审查安全前提，而不是只确认编译通过。
- FFI 边界应明确字符串表示、缓冲区所有权、错误传播、回调生命周期、线程模型和资源释放责任。
- 不要在不理解别名、未初始化内存、布局或表示约束的情况下使用 transmute、裸指针或手动内存管理。

---

## 11. 模块化与依赖

- 按领域、能力和稳定性拆分模块，不按技术细节碎片化拆分。
- 公共 API 应尽量小而稳定；实现细节留在私有模块中。
- crate 边界应对应明确的发布、复用、编译、平台或所有权边界。
- workspace 适用于共享工具链、版本策略、构建配置和发布流程的多个 crate。
- feature 应表达可选能力，而不是绕过类型系统或制造隐式行为差异。
- 依赖引入需要评估维护状态、许可证、安全记录、编译成本、MSRV、平台支持和 API 匹配度。
- 关键依赖应固定兼容范围，并定期审查安全通告和废弃状态。
- 依赖不是越少越好，而是每个依赖都应有清晰职责。
- 公共 crate 的直接公共依赖应考虑自身稳定性和下游升级成本。
- 平台特定代码应隔离到明确模块或 target 条件边界内。

---

## 12. 工具链与构建

- 使用 Cargo 统一管理构建、测试、文档、依赖、feature 和发布配置。
- 项目应声明 Rust Edition 和最低 Rust 版本。
- 公共 crate 应补充描述、许可证、仓库、文档、关键字和类别等元数据。
- 提交前运行 rustfmt；格式化差异不应进入人工代码审查讨论。
- CI 中运行编译、测试、Clippy、rustfmt 检查和文档生成。
- Clippy lint 分组应显式选择并逐项评估；不要机械接受所有建议，也不要长期堆砌无解释的 allow。
- 对安全敏感路径可考虑提高 warning 级别或使用项目自定义 lint 策略。
- 构建配置应区分开发、测试、发布和性能分析场景。
- 增量编译、缓存和依赖裁剪用于缩短开发反馈周期，但不应掩盖真实构建问题。
- 发布前应验证干净构建、目标平台构建、文档构建、测试和最小可运行示例。

## 13. 测试与审查

### 13.1 测试

- 单元测试覆盖核心逻辑、边界条件、错误路径和不变量。
- 集成测试验证公共 API、模块协作和真实使用场景。
- 并发代码覆盖竞争、取消、超时、关闭、重试和资源释放路径。
- `unsafe`、FFI 和平台相关代码必须有专项验证。
- 解析器、协议实现、输入处理、状态机和数据同步适合引入 property testing 或 fuzzing。
- 性能关键路径建立基准，并在变更前后比较数据。
- 测试应验证行为，而不是重复实现细节。
- 测试辅助代码应与生产代码一样保持清晰。

### 13.2 审查

审查至少确认：

- 所有权转移和生命周期是否清晰。
- 错误路径、取消路径和资源释放是否完整。
- 公共 API 是否稳定、语义明确、难以误用。
- unsafe 契约是否真实成立。
- 并发状态是否可推理。
- 性能改动是否有测量数据。
- 抽象是否解决当前问题，而不是堆叠假设性扩展。
- 文档、测试、日志、指标和行为是否同步。
- 第三方依赖和 feature 组合是否仍然合理。

## 14. 文档要求

- rustdoc 是公共 API 的一部分，不是附带产物。
- crate 根文档应说明用途、核心类型、主要入口、feature、平台约束和最低 Rust 版本。
- 公共 API 文档应说明语义、参数、返回值、错误、panic、安全要求、线程安全、性能特性和示例。
- 示例应尽量编译并通过 doctest；错误示例应使用惯用错误传播方式，不应鼓励 `unwrap`。
- 模块文档解释职责、边界、不变量和协作关系，不重复逐行实现细节。
- 底层算法应记录复杂度、内存行为、并发模型、失败状态和已知限制。
- 架构图、协议图或状态图只在复杂系统中维护，且必须随代码更新。
- 公共文档应链接相关类型、trait、函数和错误类型，方便导航。
- rustdoc 不应暴露无助于调用的实现细节。
- 发布说明应记录 API 变更、行为变更、废弃项、迁移步骤和安全修复。
- 团队规范与官方指南冲突时，应以官方文档为准，除非项目有明确豁免和理由。

## 15. 快速检查清单

- 命名符合 Rust 官方大小写规则。
- 转换方法符合 `as_`、`to_`、`into_` 语义。
- getter 不加 `get_` 前缀。
- 公共类型实现 `Debug`，必要时有 `Clone`、`Eq`、`Hash`、`Default`。
- 公共类型尽量支持 `Send`、`Sync`，否则明确说明原因。
- 错误类型可判断、可诊断、可传播。
- 函数验证参数并维护有效状态。
- 不使用出参；不通过布尔参数隐藏模式。
- 只在智能指针上实现 `Deref`。
- 泛型约束最小化。
- trait object 使用有明确理由。
- 克隆和堆分配有语义或测量依据。
- 析构不失败；可能阻塞的清理有替代方案。
- 异步任务考虑取消、超时和关闭。
- unsafe 有明确安全契约和专项验证。
- 构建优化配置经过基准验证。
- rustfmt、Clippy、测试和 rustdoc 都纳入 CI。
- 文档、发布说明和 API 行为保持同步。
